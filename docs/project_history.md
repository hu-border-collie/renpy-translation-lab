# 项目沿革

Ren'Py Translation Lab 的开发早于本仓库的 Git 历史。本页以脱敏后的阶段说明
项目如何从一次具体的 Ren'Py 翻译需求演化为可复用的翻译工作台；不记录私有
项目名称、本机目录、会话来源或精确任务日期。

## 从一次性任务到可恢复工作流

早期实践集中在版本差异定位、旧译复用、补丁式交付、Ren'Py 标签保护和长任务
进度保存。随后，仓库外的实验脚本逐渐加入批量请求、失败拆分、断点续跑、模型
回退和独立状态文件，形成当前同步与 Batch 路径的直接技术前身。

这些实验反复暴露了几个长期问题：

- 长任务不能依赖单次会话上下文；
- 翻译单元需要稳定身份，不能只按译文字符串定位；
- 写回前必须验证源快照、结构和结果完整性；
- 术语、上下文和质量报警需要可复查的持久化产物；
- GUI 应复用同一核心行为，而不是另写翻译语义。

## 从专用脚本到通用工具

工具最初服务于单个私有项目，后来逐步泛化为：

- 断点续传和失败记录；
- 多凭据与模型回退；
- Ren'Py 标记保护和翻译结果校验；
- 术语表、文本规范化与机械质量检查；
- Batch 工作流；
- 可选检索上下文、结构化剧情记忆和图形界面。

早期还探索过运行时翻译和其它视觉小说引擎的特化脚本，但当前主线选择预先
生成、可检查、可回滚的翻译产物。历史旁系不构成现行支持承诺。

## 设计文档的影响

仓库外的早期设计稿提出了后来持续沿用的工程方向：

- “抽取 → 去重/分批 → 回填 → 占位符校验”的分阶段结构；
- 断点续跑、翻译记忆和术语表；
- 全文上下文检索与分层提示；
- `safe / warn / block` 质检分级；
- 强制 `check → apply` 写回门禁；
- golden corpus、稳定翻译单元标识和轻量校对工作台。

这些设计经过多轮实现、测试和真实项目副本验证，以不同节奏进入当前代码。
旧设计稿只用于解释思路来源，不是现行实现规范。

## 四种“开始”

“第一个脚本”容易把不同层次混在一起。更准确的划分是：

| 层次 | 含义 |
| --- | --- |
| 问题与方法的起点 | 直接处理真实 Ren'Py 翻译任务，形成版本差异、旧译复用、补丁输出和长任务管理需求 |
| 工作流自动化的起点 | 用仓库外脚本固化解包、脚本差异和缓存清理等步骤 |
| 模型批量翻译代码的起点 | 创建项目专用批处理脚本，并在运行反馈中加入恢复与校验能力 |
| 公开 Git 历史的起点 | 将已演化一段时间的通用工具作为初始快照纳入版本控制 |

## Git 历史的开始

本仓库的根提交是公开 Git 事实：

```text
commit 59f542d8b05679417f6e428f95a34adfa89612bf
title  Initial public snapshot
```

该提交一次性纳入同步翻译、Batch、检索上下文、配置示例和项目文档等已有成果。
因此，`Initial public snapshot` 表示项目进入公开 Git 历史，而不是项目真正开始
开发的时间。

主干演化可概括为：

```text
真实翻译任务
  → 仓库外工作流自动化
  → 项目专用批量翻译原型
  → 可恢复、可校验的通用脚本
  → 公开 Git 初始快照
  → 当前 Ren'Py Translation Lab
```

## 关于历史证据

这段沿革依据权限受控的早期脚本、设计稿、运行记录和公开 Git 历史整理。原始
材料包含本机路径、私有游戏文件、运行日志和 API 配置，因此不随公开仓库提交。

现行功能、配置和安全边界始终以当前代码、`--help` 与现行文档为准；本页只用于
说明项目来源。
