# 项目沿革

Ren'Py Translation Lab 的开发早于本仓库的 Git 历史。本页简要说明项目如何从一次具体的 Ren'Py 翻译需求，逐渐演化为可复用的翻译工作台。

## 起点

项目的源头可以追到 2025 年 12 月 27 日的一次具体 Ren'Py 版本更新翻译任务。最初的设想并不是“写一个翻译程序”，而是让 Codex Agent 直接检查新旧版本、复用旧译文并补译新增内容。这次长会话逐渐形成了后来反复出现的需求：版本差异定位、旧译复用、补丁式交付、标签与缓存修复，以及长任务中的进度保存。它是项目所要解决的问题和工作方法的起点，但还不是当前脚本的代码祖先。

2025 年 12 月 28 日，Codex 又把前一天任务中的经验整理为本地 `renpy-translation-patch` Skill，并创建了 RPA 解包、`.rpy` 目录差异和 `.rpyc` 清理脚本。这是目前找到的最早一批项目相关自动化代码，也是工作流首次被产品化；不过它没有实现模型批量翻译，因此也不是后来 `gemini_translate.py` 的直接代码祖先。

2025 年 12 月末至 2026 年 1 月初，另一些 Gemini CLI 长文档任务反复暴露上下文耗尽、续跑、分块和防止破坏性改写等问题。这些经历加强了对持久化工作流的需求，但没有发现 Gemini CLI 在这一阶段直接创建本项目代码的证据。

模型批量翻译脚本这条代码主线，则始于 2026 年 1 月的 OpenCode 会话。

最早的实现并不是后来保留下来的 v2。2026 年 1 月 10 日，Codex 先创建过一个在游戏运行时调用 Google Translate 的实时翻译过滤器；用户否定了实时机翻方案，明确改为预先生成完整汉化。完成脚本解包、翻译模板和保留词准备后，Codex 创建了游戏专用的 `gemini_translate.py`（v1），通过 Gemini API 批量处理 Ren'Py 翻译文件。

v1 的初始批次和请求策略较激进，长时间运行时反复遇到断连、超时和 HTTP 429。它并非完全不能运行：原始会话保留了连续翻译数百条内容的实际输出。经过当晚迭代后，v1 还具备按批写回、跳过已有中文、拆分失败批次和记录失败原文等能力，但仍不足以稳定完成整个项目。

2026 年 1 月 11 日，在 OpenCode 的另一个会话中，用户专门追问如何让 Agent 自动完成超长任务而不退出，并要求分段汇报但无需手动输入“继续”。会话最终转向外部持久化与恢复工具的调研，虽然没有完成安装，却直接记录了后来进度状态、断点续跑和可恢复后台任务所要解决的问题。

2026 年 1 月 13 日，GLM 在新的 OpenCode 会话中检查未完成的中文文件时发现了 v1。经用户明确授权后，GLM 将它重构为 `translation_tools/gemini_translate_v2.py`，加入 API Key 轮换、模型回退、独立进度状态和更多配套文档。代码比对显示，v2 继续保留 `build_prompt`、`collect_tasks`、`process_batch` 和 `main` 等 v1 核心结构，因此 v1 是当前主线的直接代码祖先，而不是无关的一次性脚本。

GLM 的重构版看起来更加完整，但实际运行未能正确调用 Gemini API；它当时对 v1“没有断点续跑”和“失败日志不含原文”的判断也与留存源码不符。随后切换到 Gemini 接手。Gemini 重写了主要调用和处理逻辑，改用当时的官方 SDK，并根据真实运行反馈继续修复响应处理与进度输出。2026 年 1 月 14 日，这个版本首次完成真实翻译文件的连续批量处理，可以视为当前工具主线第一个得到完整运行验证的可复用祖先。

## 从专用脚本到通用工具

最初的脚本服务于单个游戏项目，后来逐步加入：

- 断点续传和失败记录；
- 多 API Key 与模型回退；
- Ren'Py 标记保护和翻译结果校验；
- 术语表、文本规范化与质量检查；
- Batch 工作流；
- RAG 上下文和图形界面。

这些工具最初集中在本地 `00_tools` 工作目录中。该目录长期持续使用，并非某一天的冻结快照。

历史上的 `gemini_translate_tyrano.py` 是针对 Tyrano 的特化旁系脚本，不属于当前 Ren'Py Translation Lab 的直接祖先。

## 设计文档也是项目来源

`00_tools` 不只是代码中转站，其中的设计文档也直接塑造了后来的功能：

- 2026 年 1 月的流水线任务说明提出了“抽取 → 去重/分批 → 回填 → 占位符校验”的分阶段结构，以及断点续跑、翻译记忆和术语表。
- 2026 年 3 月的 Batch 计划和 RAG 架构稿定义了请求分块、结果恢复、manifest 诊断、邻近上下文、历史记忆检索、写回后回灌和失败降级等方向。
- 2026 年 3 月的项目路线图及技术评审提出了 `safe / warn / block` 质检分级、强制 `check → apply` 门禁、golden corpus、稳定翻译单元标识、结构化角色/关系记忆和轻量校对工作台。

这些内容后来以不同节奏进入 Git 实现。根提交中的 `docs/roadmap.md` 本身就是 3 月路线图的精简版本；后续的安全门禁、golden corpus、identity v2、Story Memory 和 GUI 工作台，也能在这些早期文档中找到明确的设计前身。

因此，项目谱系既包括脚本之间的代码继承，也包括从 `00_tools` 设计稿到后续 Git 功能的设计继承。这些旧文档是历史依据，不是当前实现规范。

## 四种“开始”

“第一个脚本”容易把不同层次混在一起。按目前证据，更准确的划分是：

| 层次 | 时间 | 含义 |
| --- | --- | --- |
| 问题与方法的起点 | 2025-12-27 | Codex 直接处理真实 Ren'Py 翻译任务，逐步形成版本差异、旧译复用、补丁输出和长任务管理需求 |
| 工作流自动化的起点 | 2025-12-28 | `renpy-translation-patch` Skill 及其解包、差异、清缓存脚本 |
| 模型批量翻译代码的起点 | 2026-01-10 | OpenCode 中 Codex 创建的游戏专用 `gemini_translate.py` v1 |
| 公开 Git 历史的起点 | 2026-03-16 | 根提交 `59f542d`，将已经演化数月的工具作为初始快照纳入版本控制 |

## Git 历史的开始

本仓库的根提交是：

```text
commit 59f542d8b05679417f6e428f95a34adfa89612bf
date   2026-03-16T20:12:23+08:00
title  Initial public snapshot
```

该提交一次性纳入同步翻译、Batch、RAG、配置示例和项目文档等已有成果。因此，`Initial public snapshot` 表示的是项目进入公开 Git 历史的时间，而不是项目真正开始开发的时间。

可以将主干演化概括为：

```text
Codex 直接执行真实翻译任务
  形成版本对比、旧译复用、补丁与长任务需求
        ↓
Codex Skill 首次固化工作流
  解包、脚本差异、缓存清理
        ↓
OpenCode 中的翻译原型
  实时 Google Translate 方案被否定
        ↓
  Codex 创建能部分运行的游戏专用 v1
        ↓
  GLM 将 v1 重构为更完整但未能运行的 v2
        ↓
  Gemini 重写并首次成功运行
        ↓
本地 00_tools 中的代码与设计文档持续演化
        ↓
Git 初始公共快照
        ↓
当前 Ren'Py Translation Lab
```

## 关于历史证据

这段沿革依据保留的 Codex rollout、OpenCode 本地存储、Gemini CLI 会话索引、恢复出的早期 Skill、早期脚本、文件内容对比和 Git 历史整理。原始材料还包含本机路径、私有游戏文件、运行日志和 API 配置，因此不随公开仓库提交。

现行功能、配置和安全边界始终以当前代码、`--help` 与现行文档为准；本页只用于说明项目来源。
