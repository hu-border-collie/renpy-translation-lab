## C 的环境、故障与恢复边界

旧执行实际使用系统 Python 3.14 / LiteLLM 1.83.7，而仓库 Windows 哈希锁固定 LiteLLM
1.88.6，受验证的解释器是 Python 3.11。两个原生 run 都曾报
`SYNC_RUN_STORAGE_ERROR: cannot finalize run with active requests or attempts`，随后正式取消。
只读 SQLite 复核仍为 cancelled；成功 run 有 23 个有效候选，现有 `check` 为 blocked、

出站观察器仍将其保留为 `transport_unknown`；数据库分类不构成重新收费生成的依据。

初次隔离环境在 Python 3.14 上遭遇 ensurepip/TEMP 权限与安装失败，不能称为锁定环境。
续接另建仓库内 CPython 3.11.15 隔离环境，只安装
`requirements-lock/py311-windows-litellm.txt` 并要求哈希，实际为 LiteLLM 1.88.6、OpenAI
2.30.0、HTTPX 0.28.1。没有修改系统 Python 或升级依赖。尝试同时安装 CLI 与 LiteLLM
两个完整 profile 时发现其传递 pin 不兼容，保留失败日志后改按文档使用单一 LiteLLM
profile；未修改锁来掩盖安装失败。uv 下载解释器后的快捷链接创建被拒，直接核验仓库内
实际解释器并创建 venv 成功，缓存与 TEMP/TMP 均位于本轮可写目录。

在该锁定环境，用原创最小 fixture 复现并修复两处核心问题：

- LiteLLM 的一次 backend 调用在传输断开后由底层 SDK 自动尝试发送 3 次，与耐久
  attempt 的一次调用合同不符。共享 adapter 显式设置两层重试为 0；同步与异步真实 SDK

  T8 收尾。现在重新检查可派发请求；原创两请求回归确认首项失败后第二项仍正常完成，
  终态为 completed_with_errors。预算检查与写回门禁未放宽。
