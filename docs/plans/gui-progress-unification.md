# GUI 进度展示统一方案

状态：**拟定，尚未全量实施**。日期：2026-10-31。
盘点基线：`main@2bd61cf` 与当前工作区改动；现行操作仍以 [GUI 工作台](../gui_workbench.md)为准。

目标是让用户在任一页面都能看懂：正在做什么、本轮处理到哪里、已有多少成果、是否仍需处理失败项，以及下一步能做什么。
范围包括任务页、批量任务的共享状态区、项目扫描、下载和安装对话框。沿用现有 Qt 页面、主题和动作入口。
本方案依据代码盘点与已提供的关键词任务截图；其他流程的视觉与交互需在迁移时逐项补验。

## 1. 当前入口与迁移范围

当前有 7 处 `QProgressBar` 创建入口；多个任务页共用其中一处，并不等于只有 7 个业务流程。

| 入口 | 当前基础 | 迁移重点 |
| --- | --- | --- |
| [任务页共享状态区](../../gui_qt/workbench/task_controls.py) | 关键词、同步翻译、订正、上下文库等复用 `TaskStatusSection` | 统一阶段、计数、等待、结果摘要与恢复后的展示 |
| [应用壳共享进度区](../../gui_qt/app.py) | 批量任务及部分后台准备仍由宿主绘制 | 与任务页使用同一展示模型和渲染函数 |
| [工作区／SDK 准备](../../gui_qt/dialogs/workspace_setup_dialog.py) | 下载按百分比、解压按条目计数 | 阶段切换、单位、未知总量、停止后的真实状态 |
| [项目总表扫描](../../gui_qt/widgets/games_registry_panel.py) | 扫描／导入有各自的计数和文案 | 同一任务内保持分母与单位明确，保留阶段说明 |
| [字体安装](../../gui_qt/settings/appearance_page.py) | 等待下载和校验的忙碌条 | 与其他安装任务共用等待、停止、失败和完成呈现 |
| [扩展安装](../../gui_qt/settings/extensions_page.py) | 关系分析器安装有独立进度控件 | 复用安装任务展示，能力和生命周期仍归原 worker |
| [LiteLLM 安装／更新](../../gui_qt/settings/litellm_page.py) | 独立控件与状态文案 | 与字体、扩展安装保持一致 |

2026-11-01 的局部修复已让[样式模板](../../gui_qt/resources/app_template.qss)中的
`workflow_progress_bar` 与 `task_status_progress` 共用进度样式和主题 token，并将任务页进度文字独立换行。
同步关键词已分离有效结果恢复与待补队列；这不表示其他入口已完成全量迁移。

## 2. 统一计数规则

| 概念 | 展示规则 |
| --- | --- |
| 本轮处理 | 主进度条。明确本轮／本阶段的单位与分母；单元完成处理并保存后才推进 |
| 已保存记录 | 辅助数字。可能含失败记录，不能直接填满本轮进度条 |
| 已复用成果 | 单独标注复用数量与单位；请求块、初次响应、定点重试响应不能混计 |
| 有效成果 | 结果摘要。分别显示通过校验、失败、不完整和结果未知的数量 |
| 项目总体覆盖 | 仅在有权威项目分母时显示，明确区别于本轮处理与当前筛选范围 |

主条示例：`本轮待补已处理 1/113 个请求块（0.9%）`。
下方分别显示：`任务总量 768 块`、`已复用有效结果 655 块`、本轮待补组成与已保存处理记录。
完整有效比例、最终失败和不完整数量单独展示，不把已有有效块计入待补分母。
这些数字各自说明范围，不通过切换页面或进入终态，把同一条的分子悄悄换成另一个指标。

具体约束：

1. 发出请求、进入等待或开始重试都不算处理完成。完成处理的失败单元可计入“已处理”，但必须保留失败摘要。
2. 续跑开始时，本轮处理从本轮事实计算；历史记录和本轮处理分开。复用历史响应也需重新处理时，分母可包含这些单元，并明确说明。
3. 扫描时总量未知，显示“正在统计，已发现 N 个”；总量确定后再显示比例。不能把未知写成 `0/0` 或虚构百分比。
4. 下载、解压、请求、校验、写回分别是不同阶段。显示“阶段 2/4 + 本阶段计数”，不把字节、文件和请求块相加计算总百分比。
5. 等待响应时保留最后一个真实计数，说明正在等待和等待时长；没有新事实时不制造动画增长。
6. 远端 Batch 没有公开完成比例时，只显示真实远端状态与等待指示，不从等待时间推算百分比。
7. `100% 已处理`不能代替“全部有效”“索引已可用”或“允许写回”。检查、预览、写回继续遵守既有合同。

## 3. 状态与视觉

各处保持相同顺序：**阶段与状态 → 主进度条 → 本轮／历史／结果数字 → 当前事项与下一步动作**。
长路径、请求标识和详细错误放在事实区或运行日志，不挤入进度条标签。

| 状态 | 统一呈现 |
| --- | --- |
| 尚未开始 | 保持紧凑；同一项目已有结果时仍可查看 |
| 统计／准备 | 总量未知时使用忙碌指示；显示当前阶段 |
| 运行 | 使用有明确单位的真实计数；重复事件不重复累加 |
| 等待响应 | 保留计数，显示等待事项；不误报为失败或已完成 |
| 正在停止 | 保留进度，显示正在停止；等待执行器真实终态后更新按钮 |
| 已停止／可恢复 | 保留已有进度；能否恢复、派生或重试由原执行器决定 |
| 全部完成 | 显示本轮处理结果与有效成果，保留详情 |
| 部分完成 | 明确显示失败、不完整或未知项；不使用“全部成功”的文案与配色 |
| 失败／材料过期 | 保留最后可信计数与原因，提供真实可用的下一步 |

沿用现有主题 token，统一条高、轨道、填充、圆角、字体、间距和明暗主题表现。
状态同时提供中文文字，不能只靠颜色识别；进度控件的可访问名称应包含任务、单位与当前值。
窗口缩窄或系统缩放后，计数与状态不能被长路径挤掉。

ETA 只在本阶段有足够、可比较的真实样本时显示。缓存复用速度不能用于估算模型请求速度；
等待、重试、重启或阶段切换后，样本不再适用时隐藏估计。计数仍照常保留。

## 4. 数据与组件职责

以现有 [WorkflowProgressState](../../gui_qt/reports/workflow_progress.py)、
[预建进度报告](../../gui_qt/reports/bootstrap_report.py)和
[耐久 Sync 公共 snapshot](../../gui_qt/workflows/sync_translation_workflow.py)为迁移接缝。

目标结构是“执行器事实 → 流程适配器 → 统一只读展示模型 → 共用渲染组件”。
沿用现有后台任务与公开生命周期，不为统一外观重做执行器。

| 展示模型必须说明 | 用途 |
| --- | --- |
| 项目、任务类型、运行、本轮尝试与阶段身份 | 阻止旧任务、旧阶段的迟到消息覆盖当前进度 |
| 状态、计数含义、单位、当前值、总量是否已知 | 避免相同的 `current/total` 被解释成不同指标 |
| 历史记录、复用、有效、失败、不完整、未知等可选统计及各自单位 | 不具备的数据标记未知，不猜成零 |
| 当前事项、更新时间、可选 ETA 与数据来源 | 区分仍在等待、已有新响应和陈旧快照 |

实施边界：

- 优先使用公开 snapshot 或结构化进度事件。已有文本日志由适配器集中解析，页面不再各自解析。
- 适配器保留流程的权威含义；GUI 不读取耐久执行数据库、不自行重试，也不改写源快照或写回判断。
- 运行、页面往返、进程结束、重新打开工作台，都从同一展示合同恢复。空闲写回说明不能覆盖已有任务进度。
- 恢复时核对运行与材料身份；旧尝试的计数不冒充新尝试的处理量。计时与 ETA 不直接复用上次进程的时钟样本。
- 共用渲染器承接任务页与宿主的进度绘制。状态、终态和最后一次保存事件必须到达界面；沿用节流，避免每行日志触发布局重排。
- 业务计数与必要恢复信息归原执行器／产物所有；中文文案归 `user_copy.py`，视觉归主题和共享控件。

## 5. 分阶段实施

| 切片 | 范围 | 完成条件 |
| --- | --- | --- |
| P0：冻结合同与共用展示 | 明确指标与状态，整理脱敏事件夹具，补齐共用渲染与主题规则 | 同一事件序列在任务页与共享状态区得到相同计数、文案和视觉；未知数据有明确表现 |
| P1：优先迁移当前翻译主流程 | 同步关键词、耐久 Sync、原文索引／历史库预建；覆盖运行、等待、续跑和重开 | 解决已保存记录误作完成量、恢复后丢失进度、有效成果与处理量混淆；主流程可独立验收 |
| P2：覆盖其余入口 | 批量翻译／批量关键词、订正／终审、项目分析，以及 SDK、项目扫描、字体和扩展安装 | 7 处控件入口全部归入统一展示规则，各流程动作与支持边界保持清楚 |

P1 验收后再逐个迁移 P2，避免同时改动所有页面。每个切片列明已迁移入口、保留的适配器、
尚未覆盖的状态及验证结果；不把“计划已写好”或局部修复当作全应用统一完成。
索引／历史预建只覆盖用户已启用的能力；本计划不自动启用额外上下文功能或安排真实 Provider 调用。

## 6. 验收矩阵

| 场景 | 必须验证的结果 |
| --- | --- |
| 新任务 | 从本轮处理事实推进，单位与分母稳定 |
| 历史 768 条、其中有失败，再续跑 | 不在开始时满格；旧记录数不变时本轮进度仍推进 |
| 等待、超时或定点重试 | 单元保存前不提前计数；重试不重复增加分母或已处理量 |
| 全部处理但部分失败／未知 | 处理条可到终点，状态仍明确是部分完成，保留失败和未知统计 |
| 向量已保存但尚未发布完整库 | 保存进度与正式可用状态分开；完整校验前不显示库已就绪 |
| 切换页面／重新打开 | 阶段、计数含义、已有成果与恢复动作一致，不被空闲说明清除 |
| 停止与真实终态之间 | 显示正在停止；真实退出前不开放新任务或假称已取消 |
| 旧运行或旧阶段的迟到消息 | 不覆盖当前项目、运行、本轮尝试或阶段的状态 |
| 无公开比例的远端任务 | 显示等待与公开状态，不显示伪造的百分比或 ETA |
| 下载完成后校验／解压 | 新阶段明确出现，不把下载 100% 宣称为整个安装完成 |
| 明暗主题、窄窗口、缩放 | 标签可读、状态不只依赖颜色、无关键计数遮挡或截断 |

验证按三层进行：真实生产者的脱敏事件序列与统计适配测试、页面生命周期／恢复集成测试、
离线夹具驱动的视觉检查。不能仅调用进度 setter 后看到正确数字就宣告完成。
沿用[测试约定](../../tests/README.md)，优先扩展现有进度、预建、任务页、恢复、安装和主题测试；
验证使用离线夹具与模拟服务，不启动真实翻译、Embedding 或安装任务。
