# Agent 翻译工具包：方向评估与最小验证提案

> 状态：待评审、待实验验证的设计提案，尚未实现，也不是现行操作手册。
> 日期：2026-09-15。
> 评估基线：本地 `main@c690e10`，并核对远端 `main@1ddd0be` 的相关增量。
> 当前操作方式仍以 [Agent / CLI 快速开始](../quickstart_agent.md) 为准。
> 文中的工具名称、数据对象和阶段安排均为建议，尚未冻结为公共 API 或实施承诺。

## 1. 方向判断

建议优先验证以下产品定位：**宿主 Agent 负责理解作品、决定翻译策略、生成译文和审校；
本项目提供准确材料、持久成果、完整性检查和可靠写回。**

“翻译模型靠 Agent”指主 Agent 自己翻译，或委派宿主提供的子代理翻译。
工具包的基本路径应在没有项目翻译 API Key、Provider 配置和模型调用的情况下成立。
宿主仍会消耗自身模型额度，不能把项目没有 API 账单表述为翻译免费。

项目积累的抽取、条目身份、结构保护、版本对账和写回能力具有复用价值。需要通过真实任务
验证的部分，是 Agent 自主阅读、分工和审校能否减少人工介入，并改善最终译文。
现有工程测试只能支持技术可行性判断，不能证明新路线优于现有工作流。

建议先在同一仓库形成模块边界和最小闭环，完成实验后再决定独立发布、进一步拆包或调整
长期产品重心。

## 2. 从 Agent-friendly 到 Agent 使用的工具包

| 维度 | 当前主要路径 | 提议的 Agent 路径 |
|---|---|---|
| 执行顺序 | Agent 调用 CLI，程序执行预设 workflow | Agent 根据材料和结果决定下一步 |
| 翻译生成 | 项目通过 ModelProfile / ExecutionStrategy 调用模型 | 主 Agent 或宿主子代理提交译文 |
| 工作划分 | 程序构造 chunk 和请求 | Agent 选择场景或条目范围，工具冻结任务边界 |
| 上下文 | 构建计划时组装 prompt 与检索结果 | Agent 按需读取、搜索、扩展参考范围 |
| 进度 | 主要围绕 Batch job 或 Sync run | 围绕工作包、成果、审校与写回状态 |
| 模型信息 | 项目掌握请求与 Provider 回执 | 宿主可提供时记录，不可得时明确 unknown |
| 安全边界 | `check -> apply`、快照与结构门禁 | 保留相同硬约束，由工具强制执行 |

Agent 可以决定译法、翻译顺序、是否返工和怎样组织审校。工具负责条目归属、输入版本、
结果完整性、冲突检查与写回约束。这些确定性规则不随 Agent 的判断而放宽。

现有 Sync / Gemini Batch 继续作为可选执行方式，服务需要固定流程、远程排队或相应成本
策略的任务。Agent 工具包路径不以这些执行器为使用前提。

## 3. 当前基础与主要缺口

| 能力 | 当前代码 / 文档 | 复用判断 |
|---|---|---|
| 发现、候选清单、occurrence、结构验证 | [EngineAdapter 合同](../../engine_adapters/contracts.py)、[现行边界](../engine_adapter.md) | 适合作为核心，保留引擎能力差异 |
| 声明式写回与事务 | [writeback.py](../../engine_adapters/writeback.py)、[atomic_io.py](../../atomic_io.py) | 复用计划校验与事务能力，完整门禁仍须接入 workflow/common 层 |
| 源快照、版本对账、译文复用 | [versioning.py](../../engine_adapters/versioning.py)、[reuse.py](../../engine_adapters/reuse.py) | 支撑任务身份、源变更检测与跨版本资产 |
| 外部订正提案 | [revision_corpus.py](../../revision_corpus.py)、[revision_proposals.py](../../revision_proposals.py)、[订正工作流](../batch_workflows.md) | 已有语料导出、Agent 提案、身份及快照校验，是初译入口的参考 |
| 初译手工导入 | [import_manual_translations.py](../../import_manual_translations.py) | 可验证桥接，但尚不是正式的外部成果合同 |
| 上下文材料 | [advanced_context.py](../../advanced_context.py)、[rag_memory.py](../../rag_memory.py)、[上下文系统](../context_systems.md) | 整理为可查询材料，让按需读取与自动装配能分开使用 |
| 机器接口 | [cli_contract.py](../../cli_contract.py)、[cli_discovery.py](../../cli_discovery.py) | 复用 JSON envelope、稳定错误分类、输出裁剪与机器发现 |

目前有四处需要实质调整：

- [TranslationPlan](../../translation_plan.py) 同时冻结源身份、模型快照、执行策略、
  chunk、上下文和请求。它适合当前执行器，外部 Agent 工作包需要更独立的输入合同。
- 初译手工导入把译文包装为 Batch response，并设置 `JOB_STATE_SUCCEEDED`。正式入口需要
  表达外部来源、部分提交和接收状态，不能把包装状态当成 Provider 执行证据。
- [SyncRunStore](../../sync_run_store.py) 的租约围绕单个 run 的调度器设计，
  [SyncRunService](../../sync_run_service.py) 消费冻结的执行计划。耐久化经验可以复用，
  但不能直接视作多个宿主 Agent 的任务领取协议。
- 当前同步路径在计划构建阶段集中检索，历史回灌主要发生在 apply 后。串行 Agent 需要
  读取尚未写回的中间成果，不能依赖修改游戏文件来共享最新译文。

首个验证范围限定 Ren'Py。TyranoScript 已有 Adapter 能力，但 CLI / GUI 产品接入与
端到端边界不同，不能从协议存在推导出第二引擎已经具备同等工具包支持。

## 4. 职责与交付边界

| 层 | 职责 | 主要输出 |
|---|---|---|
| 用户 / 宿主 | 翻译目标、可用模型与额度、子代理能力、操作授权 | 本次任务约束 |
| 主 Agent | 理解作品、选择范围、安排串并行、协调术语、判断返工和审校 | 任务分配、翻译决定、审校结论 |
| 翻译 / 审校子代理 | 在明确范围内读取材料、翻译或提出订正 | 完整结构化成果、疑点与建议 |
| 工具包核心 | 材料身份、版本、成果接收、覆盖检查、预览和写回 | 持久状态、诊断、回执 |
| 可选执行器 | 转换并执行项目管理的 Sync / Batch 请求 | 同一成果合同的输入 |
| CLI / MCP / GUI | 暴露与展示共享服务 | 与核心一致的操作结果 |

宿主负责启动子代理、选择实际可用模型和执行额度限制。工具包不能假定任意宿主都支持
子代理、指定子代理模型、长期运行或精确用量回传。单 Agent 串行路径必须能够独立完成任务。

建议交付形态为共享 Python 核心、精简 CLI 和使用技能，按实际需要增加 MCP 薄封装。
技能描述阅读、分工、恢复与交付习惯；身份和写回检查落在代码中。MCP 是连接方式，
翻译状态和 Agent 调度仍需要明确的业务边界。

GUI 可继续承担候选选择、质量报告、问题定位和写回预览。新增共同能力须遵循
[CLI / GUI 同步约定](../../CONTRIBUTING.md)；纯 Agent 工作包交换等高级入口若先仅提供
CLI，应在实施范围中明确例外及原因，不能静默形成两套翻译行为。

## 5. 工作包、成果与进度合同

以下描述逻辑对象，不规定最终文件名、存储引擎或完整 schema。

### 5.1 工作包：需要完成什么

| 信息组 | 建议携带的信息 |
|---|---|
| 身份 | schema 版本、项目身份、工作包 ID / digest、引擎与 Adapter 版本 |
| 目标范围 | 有序 occurrence ID 集合、目标语言、范围选择条件、源快照 |
| 每个条目 | 原文、可得的人物和场景信息、现译及其版本、结构约束 |
| 参考材料 | 相邻场景、术语、风格说明、已审校译文的引用与版本 |
| 交付要求 | 必须返回的条目、允许的逐条处置类型、成果 schema |

目标条目与只读参考条目必须分开。相同原文在不同位置仍保留不同 occurrence，不能按文本
去重。Agent 可以调整任务范围，工具负责验证并冻结；已发布工作包发生变化时应生成
新版本或派生包，不能原地悄悄改写。

工作包不要求绑定 Provider 或固定 prompt。可选执行器可以据此生成 TranslationPlan；
外部 Agent 路径记录实际可观测的输入和来源，不补造完整宿主 prompt。

### 5.2 成果：提交了什么，针对哪个版本

一次提交应绑定工作包 digest、提交 ID 和条目身份，并携带译文、所依据的现译版本、
必要的疑点或处置理由。术语和风格变更建议作为独立提案接收。

建议采用以下接收语义：

1. 校验类型、条目归属、源版本、现译版本和结构约束，再进入候选存储。
2. 允许部分提交；缺失项继续计入未完成，不能因结果文件存在而关闭任务。
3. 同一提交 ID、相同内容重放返回原回执；相同 ID、不同内容返回冲突。
4. 同一条目的竞争译文保留为候选冲突，不能按到达顺序静默覆盖。
5. 未知 ID、跨项目提交、源或现译过期给出具体诊断，不能用强制覆盖消除。
6. “暂缓”“不翻译”等处置须有明确理由并符合范围规则，不能绕过 coverage blocker。

接收幂等性只约束工具如何处理成果，不承诺模型生成恰好执行一次，也不承诺宿主不重复计费。

### 5.3 进度：保存可恢复事实

建议分别保存三个维度，避免用单一 `done` 混合不同含义：

| 维度 | 要区分的事实 |
|---|---|
| 成果完整性 | 未提交、部分提交、接收有效、冲突、过期 |
| 语义审校 | 未审、存在疑点、已审校，以及审校者和材料版本 |
| 写回 | 未写回、允许写回、已写回、恢复待完成 |

“接收有效”只表示成果符合相应输入和结构合同，不代表语义质量合格。
已审校但尚未写回的译文可以供后续任务参考；读取草稿时必须明确其审校状态。
RAG 可以索引这些成果，但不成为成果是否存在或是否通过审校的唯一事实来源。

进度查询应列出已交付、缺失、冲突、待审与待恢复范围。新 Agent 能依据这些持久事实
继续工作，不依赖上一段聊天记录或子代理的完成摘要。

## 6. 串行、并行与混合翻译

### 6.1 单 Agent 串行

1. 读取项目清单和关键参考，按需要先了解全章或整条人物线。
2. 选择场景或条目形成工作包，按需查询更远的上下文。
3. 提交译文与疑点，处理工具返回的结构、缺项或版本问题。
4. 审校并保存术语、风格决定，供后续工作包引用。
5. 继续下一范围，最后进行跨场景复查与统一写回。

无需每完成一包就 apply。术语或剧情解释变化时，应定位受影响的已译范围并安排复审；
后续章节提供的新信息可能要求修改前面的译文。

### 6.2 子代理并行

首版建议采用明确范围、独立成果文件、集中接收的方式：

1. 主 Agent 确定共同的术语、风格和参考版本，划分工作范围。
2. 子代理读取各自工作包，可以查询公共材料，分别输出完整成果文件。
3. 主 Agent 顺序调用统一接收入口，处理冲突、遗漏与术语提案。
4. 对汇总结果进行跨范围审校，再统一检查和写回。

子代理成果文件不能互相覆盖，也不直接修改共享游戏文件、术语表或权威进度。
共享参考由协调者确认并发布新版本；在途工作包保留旧版本依据，受影响的成果进入复审范围。

同源的多个包可以并行生产候选，但单包写回可能使其他包的源快照过期。首版优先汇总后
写回；确需中途写回时，剩余工作必须重新核对或派生任务，不能绕过 stale 检查。

出现多个协调者动态领取任务的实际需求后，再设计领取租约、失联回收和迟到成果规则。
首版不需要自建通用多 Agent 调度平台。

### 6.3 执行策略选择

| 材料特征 | 优先尝试的方式 | 需要观察的风险 |
|---|---|---|
| 连续对话、伏笔和人物关系高度相关 | 串行或先统一理解后分工 | 后续信息导致前文返工 |
| 相对独立的路线、支线或材料组 | 小规模并行初译 | 称谓、人物口吻与术语漂移 |
| 关键场景存在多种解释 | 集中审校或独立复审 | 多个 Agent 共享同一错误前提 |
| 内容量大、语义依赖较低 | 并行与可选执行器均可比较 | 上下文重复、额度与汇总成本 |

任务边界可以采用引擎可得的场景、label 和条目集合，不要求先构建完整剧情图谱。
并行度由主 Agent 结合依赖和宿主约束决定，不能预设“子代理越多越好”。

## 7. 工具接口形态

以下是能力分组及示意名称，**不是当前可执行命令**：

| 能力组 | 示意操作 | 结果要求 |
|---|---|---|
| 项目检查 | `project.inspect` | 引擎能力、范围、coverage 与必要准备状态 |
| 材料阅读 | `source.read` / `source.search` | 选中条目及必要上下文、来源、版本与截断信息 |
| 工作包 | `work.export` | 冻结 Agent 选定的条目和参考依据 |
| 成果与进度 | `work.submit` / `work.status` | 回执、缺项、冲突、过期与可恢复状态 |
| 共享参考 | `reference.read` / `reference.propose` | 查询版本化参考，接收待确认变更建议 |
| 检查与交付 | `check` / `preview` / `apply` | 复用既有门禁、绑定预览与写回服务 |

工具围绕 Agent 的实际操作设计，不把全部内部函数或既有子命令逐一暴露。
可组合确定性的读取与整理步骤，减少为拼接材料而多次往返。

大结果支持分页、范围查询和制品引用；常用结果提供摘要，需要时再读取详细条目。
必须保留稳定 ID、材料版本、截断状态和错误分类，不能因省略信息制造“全部材料已读完”
或“任务已完成”的假象。

基本路径不隐式调用翻译、Embedding 或 Project Analysis 模型。文本检索与已有材料读取
应能离线使用，可选模型能力的调用与消耗单独表达。

## 8. 检查、写回与质量验收

外部译文与项目模型生成的译文遵守同一写回边界：

- 只有与当前 manifest/results 匹配的最近一次检查满足
  `writeback_gate.decision=allow` 时才允许写回，并按对应流程消费绑定预览。
- 源快照、项目身份、结果身份、Adapter 结构验证和 WritebackPlan 校验继续生效。
- `quality_gate` 报警默认不阻断写回；项目配置提升为 blocker 的规则必须阻断。
- `--force` 不得绕过 stale check、源快照变化、结构阻断或结果冲突。
- 写回与后续状态推进使用可恢复事务和回执；中断后区分文件已提交与状态仍待补记。

现行 Adapter 渲染层不持有 writer。完整写回还涉及 workflow/common 层的身份、结果绑定、
实时源复核、事务与状态推进。外部成果可以桥接既有 workflow，也可以经抽出的共享服务
接入；实施前必须确定复用点，不能仅复用渲染器，另建一条检查较少的写回路径。

完成报告分别说明命令执行、机械检查、语义审校和实际游戏验证。coverage 有扫描边界，
界面、字体、图片文字、动态显示和运行问题仍需独立检查。未执行的项目标为未验证。

## 9. 最小验证增量

目标是：**在没有项目翻译 API 配置的情况下，由 Agent 完成一个 Ren'Py 章节的初译、
订正和安全写回，并验证串行与小规模并行使用同一成果合同。**

建议实施顺序：

1. 明确初译工作包和外部成果合同，复用 occurrence、快照及订正提案的验证经验。
2. 提供导出、接收与状态入口，支持部分提交、幂等重放和具体冲突诊断。
3. 桥接既有检查、预览与写回能力，验证恢复和错误路径。
4. 提供最小使用技能和示例，以串行、独立子代理成果两种方式完成同一闭环。
5. 根据真实使用记录调整工具粒度，再决定是否增加 MCP 或更复杂的任务领取能力。

首版暂不包含跨宿主调度、动态抢任务、自动模型选择、通用 Agent runtime、全自动剧情图谱、
第二引擎产品接入或全面 GUI 重构。现有模型配置和默认策略保持独立演进。

### 9.1 工程验收

| 验收点 | 必须观察到的结果 |
|---|---|
| 无项目模型调用 | 关闭项目模型能力后仍完成基本路径；隐藏的 Embedding / 分析调用也会使验收失败 |
| 输入与范围 | 重复原文保留不同 occurrence；未知 ID、跨项目及范围外结果被拒绝 |
| 部分提交 | 状态列出剩余条目，不能标记整包完成 |
| 重复与竞争提交 | 相同提交重放有稳定回执；不同内容或竞争译文不静默覆盖 |
| 版本失效 | 源、现译或工作包变化后给出 stale / conflict，不能强行写回 |
| 串行参考 | 未写回的已审校译文可供后续读取，状态与参考版本可追溯 |
| 并行隔离 | 子代理成果互不覆盖；汇总后无漏项，术语提案有明确处置 |
| 中断恢复 | 接收或写回中断后可查明状态并继续，不能用聊天摘要证明完成 |
| 既有门禁 | stale check、结构 blocker、源复核与 `--force` 回归继续通过 |
| 用量事实 | 宿主未提供模型或用量时显示 unknown，不填零成本或虚构 Provider 成功记录 |

先测试合同及实际复用的执行路径，再按改动范围运行 CLI / GUI 门禁。离线测试可使用人工
构造译文验证工具合同；翻译质量需要真实 Agent 执行和独立审阅。

### 9.2 产品实验

先选择完整章节及跨章节关联片段，使用隔离副本比较：

| 路线 | 用途 |
|---|---|
| A：直接 Agent 处理项目 | 观察专用工具对完整性、恢复和人工介入的增益 |
| B1：Agent + 工具包，串行 | 验证自主阅读、翻译和成果持久化 |
| B2：Agent + 工具包，小规模并行 | 在 B1 基础上测量耗时收益与一致性代价 |
| C：现有完整工作流 | 保留当前产品路线的交付与成本基线 |

模型、目标语言、风格、资料权限与预算尽量可比。无法使用相同模型时，只比较整条路线，
不把差异直接归因于架构。验收清单独立于各路线自己的完成报告。

记录人工介入时间、总耗时、失败与重试、实际成本或额度、遗漏与运行问题，以及匿名
译文审阅结果。重点抽查人物口吻、反讽、术语、跨章节指代和上下文依赖。
使用既有 [A/B 实验能力](../../translation_ab_experiment.py) 时，应明确其覆盖的请求或
上下文变体，不能把局部比较视为完整 Agent 路线实验。

带着验证目的完成实际翻译，交付质量优先。章节结果值得继续时，再运行完整作品，观察
长期一致性、恢复成本和累积遗漏。若工具调用负担抵消收益，应先收缩接口；若并行只增加
返工，应降低并行度。

## 10. 后续决策与投入取舍

最值得继续积累的是抽取完整性、结构验证、版本化资产、可恢复成果和游戏交付验证。
固定分块、自动摘要、RAG 装配与 Provider 执行器可逐步成为按需能力。

新增 Provider 协议、更多默认策略或复杂上下文编排不应成为最小实验的前置条件。
其投入分别由现有产品需求和实验数据决定；本文不变更既有 issue 的范围或状态。

尚待实施设计或实验回答的问题：

- 初译成果接收如何复用订正合同，并避免复制 Batch / Sync 的写回逻辑？
- 工作包和参考版本采用什么粒度，才能检测 stale 并减少无关返工？
- 如何定位术语更新影响的已译范围，区分必须重审与仍可使用的成果？
- 第一种目标宿主能稳定提供哪些模型、子代理、制品交换和用量信息？
- 哪些候选审阅和状态展示可复用 GUI，哪些操作明确属于高级 CLI？
